# 第 08 轮 · 体验与界面发现（UX）

侦察者：`r8-ux`。只读 `src/`、`host/`。基线 commit `d65164a`（0.20.0）。
环境：应用 `http://localhost:5173`，CDP `http://127.0.0.1:9223`（headless Edge 157），未跑 `npm run build`，未装依赖。

**结论（三条）**

1. 关闭保护现在**完全不存在**：浏览器没有 `beforeunload`，宿主没有 `FormClosing`。三按钮对话框只有宿主能做，浏览器只能拿系统提示。宿主模式还不写草稿（`App.tsx:589-596`），所以宿主关闭文案**不得**承诺「草稿会保留」。

3. 文件菜单宽度不够，最长一项已折成三行（`打开文件夹…` 高 94 px）。「最近打开」要在这里加 8 条长文件名，必须先改宽度与截断，否则菜单会变成一片换行。

方法与证据目录：

- 截图 `shots/round-08/`。`10/11/14/15/16` 是**运行时注入的 mock 原型**（不是已实现的样子），其余是现状实拍。

## U1 关闭保护：宿主静默退出，浏览器无拦截；三按钮对话框只有宿主能做

**证据**
- 全仓 `rg beforeunload` 在 `src/`、`host/` 零命中。运行时注入探针（`EventTarget.prototype.addEventListener` 计数）在页面里数到 1 次注册，但 `src/` 无该调用，判断来自开发工具（Vite 客户端），来源未进一步定位。
- `host/Program.cs:109-133`：`form.FormClosed += delegate { Log("form closed"); }`（131 行，只记日志）。没有 `FormClosing`，没有 WebView2 的 `WindowCloseRequested`。点关闭直接退出。
- 现有保存/切换确认：`App.tsx:3037-3047`（取消 / 放弃改动 / 保存并切换），`App.tsx:3006-3011`（草稿确认）。关闭是唯一没有确认的出口。
- 实测（`.tmp/ux-probe2.mjs`）：写 5 个字后 `window.__slState.dirty === true`，`window.onbeforeunload === null`，顶栏 dirty 点出现（`.dirty`，5×5 px，`title="有未保存的改动"`，`08-topbar-dirty-1440.png`）。

**用户影响**：写作者最怕的损失，且发生在最容易发生的动作上（改完点右上角 ×）。数据安全，不是外观问题。

**改法与文案**

浏览器场景（只能给系统提示，文案不可控）：
- 条件：`dirty` 为真时注册 `beforeunload`；不 dirty 不注册，正常关闭不打扰。
- 不要指望自定文案。Chrome 显示系统串（「离开此网站？所做的更改可能不会保存」），自定义文字被忽略；所以浏览器端**不做**三按钮。
- 宿主关窗由 C# 销毁 WebView，页面 `beforeunload` 在 WebView2 里不可靠（不弹系统确认框）。宿主必须自己钩 `FormClosing`，不要指望页面拦截。
- 兜底靠草稿：浏览器模式每次按键都写 `localStorage['sidelight.doc.v1']`（`App.tsx:592`，实测每键一次），重开可恢复。这条可以写在提示里。

宿主场景（唯一能做三按钮的地方）：
- 钩子：`form.FormClosing` 里 `e.Cancel = true`，向页面发 `{type:'close-request'}`；页面回 `{type:'close-confirm'|'close-cancel'|'close-saved'}`。页面对应 `App.tsx` 的 webview 消息分支（现在只处理 `save-result`，`App.tsx:1814-1844`）。
- 首帧先把答案定在「取消」（关窗是最容易误触的按钮，`e.Cancel = true` 是安全默认）。

对话框文案（推荐直接采用）：

| 位置 | 文案 |
| :--- | :--- |
| 标题 | 这篇还有没保存的改动 |
| 正文（宿主，无可写句柄） | 「第二章 长夜里的灯与那些没有说完的话.md」有改动还没写回文件。现在关窗，这些改动会丢失。 |
| 正文（宿主，有可写句柄） | 「X.md」有改动还没写回文件。现在关窗，改动会丢失；点「保存并关闭」会写回原文件。 |
| 正文（浏览器，草稿已确认写入） | 「X.md」有改动还没写回文件。关掉后可以从本机草稿恢复（保存于 14:32）。 |
| 按钮（左→右） | 取消 · 不保存 · 保存并关闭（主按钮最右，默认焦点） |

按钮顺序按现有约定：`.dialog-actions` 右对齐、取消在左、主按钮在右加 `.primary`（`App.tsx:3037-3047`，`styles.css:899-904`）。不要用「放弃改动」，与 Windows 惯例同词：「不保存」。同时把现有切换文档对话框的「放弃改动」改成「不保存」，两处用一套词（`App.tsx:3042`）。

「草稿会保留」只在**确实有草稿**时才写：
- 浏览器模式：草稿每次按键写入，「关掉后可以从本机草稿恢复（保存于 HH:MM）」成立。
- 宿主模式：**不成立**。`App.tsx:589-596` 明确不写 `localStorage`，`.sidelight/drafts` 也需要文件目录句柄（`App.tsx:598-609`）。所以宿主文案写「会丢失」。
- 想对宿主也承诺草稿，必须先让宿主模式也写 `.sidelight/drafts`，并验证写入成功后再改文案。本轮不建议（多一条写盘路径 + 失败态）。

难度：宿主 **中高**（C# 钩子 + 协议往返 + 焦点管理）；浏览器 **低**（`useEffect` 加一个监听，约 10 行）。
验收：宿主写 3 字 → 点 × → 出现对话框；点「取消」窗口还在、正文还在；点「不保存」窗口关闭；点「保存并关闭」→ 文件 mtime 变、重开内容一致。浏览器写 3 字 → 刷新 → 出现系统确认。

## U2 设置面板再加一行会裁掉「保存」按钮（1366×768 已临界）

**证据**（`.tmp/ux-probe5.mjs`，干净基线，每档新开页面）

| 视口 | 现状面板高 | 上边 | 保存按钮底 | 加一行后高 | 加一行后上边 | 加一行后保存按钮底 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1440×900 | 780 | 60 | 773 | 848 | 26 | 853（放得下） |
| 1280×800 | 780 | 10 | 769 | 832 | −16 | 795（刚好） |
| 1366×768 | 780 | **−6** | 753 | 832 | **−32** | **779 > 768（被裁）** |
| 1024×768 | 780 | **−6** | 753 | 832 | **−32** | **779 > 768（被裁）** |

- `.dialog` 没有 `max-height`、没有 `overflow`（`styles.css:849-856`，实测 `overflow-y: visible`）。溢出时上下两端一起出屏，**无法滚动**。
- `.shortcuts-dialog` 有现成规则：`max-height: 82vh; overflow-y: auto`（`styles.css:1038-1042`）。也就是说这个坑早有人踩过，只是没修到 `.dialog`。
- 截图：`17-settings-baseline-1366x768.png`（标题「设置」上沿已被切）、`18-settings-plus-row-1366x768.png`（加一行后标题切一半、`保存` 按钮出屏）、`15/16-settings-mock-*-1440x900.png`（1440 下的加行与滚动效果）。

**用户影响**：1366×768 是 Windows 笔记本最常见分辨率。自动保存开关放进去后，用户改完设置找不到「保存」，会以为没生效。这是本轮新功能的直接阻断。

**改法**
1. `styles.css:849-856`：`.dialog` 加 `max-height: calc(100vh - 40px); overflow-y: auto;`，删掉 `.shortcuts-dialog` 里重复的两行（顺带修掉现在的 6 px 裁切）。
2. `.dialog-actions` 加 `position: sticky; bottom: 0; padding-top: 8px; background: var(--paper-raised);`——否则加了滚动后「保存」仍在折叠线以下（实测 1440×900 滚动后才看得到）。
3. 自动保存不放在「批注提示词」后面。设置面板现在是 7 个平铺字段、没有分组（`SettingsDialog.tsx:43-148`）。建议加两个小标题（复用 `.shortcuts-group h3` 的样式，`styles.css:1044-1048`）：
   - 「外观与保存」：主题、正文字号、**自动保存**
   - 「AI 与批注」：接口地址、API Key、模型、联网核对、批注提示词
   只加标题、不移动现有字段也可以（放在「正文字号」下面，离主题近）。
4. 主按钮改名：「保存」→「保存设置」。现在这个按钮与文件保存同名同字，加了自动保存开关以后更容易误读（`SettingsDialog.tsx:167-169`）。

难度：**低**（两处 CSS + 一行 JSX + 两个 h3）。
验收：1366×768 下打开设置，标题完整、`保存设置` 可点；1440×900 与 1280×800 各截一张图。

## U3 自动保存：状态栏有的是地方，风险是「看不见」与「太吵」，不是拥挤

**证据**
- 状态栏现状（`StatusBar.tsx:14-32`）：
  - 左：`146 字 · 阅读约 1 分钟`（117 px）、`元数据` chip、`保存到 <文件名>` chip（`StatusBar.tsx:20-24`）。
  - 右：`草稿 14:32`（`App.tsx:2974-2976`）、`源码` / `预览` / `专注` / `打字机`。
  - 高 28 px、字号 12 px（`styles.css:1216-1227`）。
- 实测空隙：1440 宽右侧空 1299 px；1280 宽空 1139 px；1024 宽空 765 px，`.status-right` 宽度为 0。
- Mock（`.tmp/ux-probe3.mjs`）：加「已自动保存 14:32」→ 左侧 235 px；最坏情况（30 字长文件名 chip + 保存状态）611 px，1024 宽仍不溢出、不换行（`12-statusbar-autosave-1280.png`、`13-app-statusbar-autosave-1440.png`）。**状态栏不会拥挤，不需要缩字号或隐藏模式 chip。**
- 现有保存成功提示是常驻 toast（`App.tsx:1560-1565` `persist: true`，`App.tsx:1804`）。自动保存若也弹 toast，会变成每条都挂一个。「已自动保存」**只能进状态栏**，不进 toast。

**用户默认预期**：写作应用默认自动保存（Typora 常开、Obsidian 默认开、Word/Notion 默认开）。**默认开**。不开才是意外。
但默认开有代价：不能写用户没打算改的地方。边界与 brief 一致，只补一条用户能看见的规则：

- 有可写句柄 / 宿主可写 → 停笔 2 秒后自动写盘。
- 新建的、没保存过的文档 → **不**自动写盘，状态栏显示 `未保存 · Ctrl+S 选位置`（点一下等同按保存）。
- 有未确认的结构损失（引用式链接/表格，`App.tsx:1709` 的差异门）→ **暂停**自动保存。否则第 7 轮的差异门会被自动保存绕过，等于白做。
- 宿主报 `PATH_CHANGED`（外部改过）→ 暂停，不覆盖别人的改动。

**开关位置**：`SettingsDialog.tsx` 的「外观与保存」组末尾，紧跟「正文字号」。复选框 + 一行 hint：
- 标签：`自动保存`
- 提示：`停笔 2 秒后写回文件。没有保存过的文档不会自动写盘。`
- 默认：`DEFAULT_SETTINGS` 加 `autoSave: true`（`lib/settings.ts:26-35`）。`loadSettings` 里读不到旧值时按 `true`（老用户升级后默认开，符合预期）。
- 关闭后：状态栏不再显示保存状态；顶栏 dirty 点保留（它是唯一「有改动」信号）。

**状态栏状态表**（左侧，紧跟 `保存到 X`；宽度实测都放得下）

| 状态 | 文案 | 样式 | 点击 |
| :--- | :--- | :--- | :--- |
| 已写盘 | `已自动保存 14:32` | `status-chip-quiet` | 无 |
| 写盘中，超过 1 秒 | `正在保存…` | `status-chip-quiet` | 无 |
| 没有落点 | `未保存 · Ctrl+S 选位置` | `status-chip-quiet` | 等同保存 |
| 差异门未确认 | `自动保存已暂停 · 结构会改写` | 警示色 chip | 打开保存确认框 |
| 外部修改 | `自动保存已暂停 · 文件已被外部修改` | 警示色 chip | 「另存为」 |
| 写盘失败 | `自动保存失败 · 重试` | 警示色 chip | 重试 |

不吵的四条规则：
1. 保存中不显示，除非超过 1000 ms（宿主写回可能慢）。大多数自动保存不可见。
2. 成功只更新时间文本，不弹 toast、不闪、不做动画。
3. 失败先只把 chip 变警示色，并**停止自动重试**（避免循环写盘）。用户点「重试」再失败一次，才升级成现有错误提示（常驻 + 「另存为」动作，`App.tsx:2834-2843` 的 banner 或 `kind:'error'` toast）。
4. 时间格式复用现有 `toLocaleTimeString('zh-CN', { hour: '2-digit', minute: '2-digit' })`（`App.tsx:2975`），保证与 `草稿 14:32` 同一写法。

失败文案：复用 `hostErrorCopy`（`App.tsx:218-239`）的句式与 `保存失败：<原因>。改动还在，可以再试一次。`（`App.tsx:1611`）。只读、文件不存在、编码这三类不可恢复，直接给「另存为」，不给「重试」。

难度：状态显示 **低-中**（`StatusBar` 加一个 `saveState` prop）；「暂停」判定 **中**（要接差异门与 mtime，缺陷组同题，别两边各写一套）。
验收：改一个字 → 等 2 秒 → 状态栏出现时间；再改字 → 时间变化且不弹 toast；把文件设为只读 → 状态栏出现失败 chip 且只出现一次。

## U4 文件菜单放不下「最近打开」：现在最长那一项已经折成三行

**证据**
- 实测（`.tmp/ux-probe.mjs`）：`.file-menu` 173×194 px，`.file-menu-wrap` 只有 59 px 宽（`position: relative`，绝对定位子元素按它做 shrink-to-fit）。末项 `打开文件夹…` 高 **94 px**（三行），`kbd` 宽 103 px。
- 截图 `05-filemenu-1440.png`：`打 / 开文件 / 夹…` 竖排折行，键位掉到左侧。
- 成因：`.menu` 只给了 `min-width: 136px`（`styles.css:1009`），`.file-menu button` 是 `space-between` 弹性行（`styles.css:1023-1029`），`kbd` 不可断行，于是标签被压到折行。
- 修法实测：`.file-menu { width: max-content; min-width: 210px }` + `.file-menu button > span { white-space: nowrap }` → 菜单 223×130，末项回到 30 px（`10-mock-recent-submenu-1440.png` 里就是修过的菜单）。

**层级与条数（建议内联，不做 flyout 子菜单）**
- 理由：`FileMenu.tsx:84-106` 的键盘处理只有 ↑↓ / Home / End / Tab / Esc。flyout 要再加 →← 进入/退出、hover 延时、右边界翻转，三样都是新代码新 bug。内联只多 6 行 CSS。
- 结构：4 条动作 → 分隔线 → 小标题 `最近打开` → 最多 8 条 → 分隔线 → `清除最近打开`。
- 高度预算：4×30 + 8×30（8 条）+ 标题与两条分隔线 + 内边距 ≈ **430 px**。菜单从 y=38 起，1366×768 下仍有余量（可用 730 px）。截图 `10-mock-recent-submenu-1440.png` 是 380 px 宽的 flyout 版，只用来验证长名截断，不要照抄层级。
- 条数：存 8、显示 8。去掉「更多」这一层。
- 空态（`11-mock-recent-empty-1440.png`）：一条不可点的灰行 `还没有打开过文件`，不显示 `清除最近打开`。不要用禁用样式的假条目。
- 清除入口：分组最后一条，分隔线下方。不做二次确认（代价只是丢列表），清完立刻切空态、焦点回「文件」按钮。

**文件名过长**
- 一行、`text-overflow: ellipsis`、`title` 放完整名。实测 318 px 内容宽下，近 30 字的中文名 `scrollWidth 324 > clientWidth 318` 正好截断（`10-mock-recent-submenu-1440.png` 第 2 条、第 6 条）。
- 右侧固定一列相对时间：`10 分钟前` / `今天` / `昨天` / `3 天前`。不写完整日期，不写时间戳。
- 只显示文件名 + 父目录名，不显示盘符全路径（`App.tsx:186` 的设计就是页面不拿完整路径）。同名文件靠父目录区分，父目录放第二行或 `title`。

难度：菜单宽度与截断 **低**；最近打开列表 + 键盘 **中**（`FileMenu` 要接受外部数据、焦点归还、空态）。
验收：1440 / 1280 / 1366×768 各截一张打开状态的图；8 条里含一条近 30 字中文名；空态一张。

## U5 最近文件缺「点了能重新打开」的数据源；空态与失效提示必须诚实

**证据**
- 页面拿不到路径：`/__doc` 只回 `fileName`、`mtime`、`readOnly` 等字段，没有 path（`App.tsx:186-215`）。
- 宿主只认两种入站消息：`forget`（`host/Program.cs:556`）与 `save`（`App.tsx:1763`）。没有「按路径打开」，也没有「最近列表」。
- 浏览器句柄不落库：`src/lib/workspace.ts` 全文件无 `indexedDB`，`FileSystemFileHandle` 只活在内存与 React state 里。刷新即失效（重新授权要用户手势）。
- 结论：`最近打开` 的**菜单本身**一天能画完；「点一条能打开」需要新数据通道。不做通道就上线，等于给一个所有条目都点不动的菜单。

**两条可选路线（都要改宿主或加存储，属缺陷/实施组范围，这里定体验要求）**
1. 宿主侧记录（推荐，Windows 首发场景）：宿主把成功打开过的路径写进数据目录的一个 JSON，经 `GET /__recent` 回传 `[{ name, parent, mtime, miss }]`；页面点一条时发 `{type:'open-path', path}`，宿主载入后仍走 `/__doc`。显示名与父目录**只由宿主给**，页面不拼路径。
2. 浏览器侧 IndexedDB 存 handle：能存，但每次重开要 `requestPermission`，Chrome 会弹一次授权。不能承诺「点了就开」。

**界面要求（不管走哪条，这几条不变）**
- 空态与「没有数据源」分开：没有数据源时整组不渲染，而不是显示空列表。
- 路径失效：点击不存在 → 不开对话框，用现有错误提示样式（`kind:'error'`，常驻）：
  - 文案：`这个文件已经不在了：<文件名>。可能被移走或改名。`
  - 动作：`从列表移除`
  - 宿主侧可复用 `FILE_GONE` 的判定（`App.tsx:226-227` 已有同类文案）。
- 隐私：`清除最近打开` 必须真的删记录（宿主 JSON 与 localStorage 两处），不是只清界面。
- 列表只记「用户主动打开过的文件」，不记自动保存碰过的路径。

难度：**高**（跨 host + page + 存储，且要处理失效、权限、隐私三件事）。若本轮时间不够，建议只做「菜单 + 宿主记录 + 失效提示」，浏览器端不显示这一组，并在 CHANGELOG 写明。

## 附：界面代码优化机会（3 条）

**O1 每次按键都整篇序列化并同步写 `localStorage`（性能热点，自动保存上线前应先修）**
`App.tsx:578-596` 的 `onUpdate` 里，每次输入都跑 `getMarkdown()` → 四个 `repair*` → `joinFrontmatter` → `JSON.stringify` → `localStorage.setItem`。实测连敲 5 个字符产生 **5 个不同的 `savedAt`**（`.tmp/ux-probe2.mjs` 的 `draftWriteTicks`，5/5 各不相同），即 5 次整篇序列化写盘。本轮要再加一条自动保存写盘路径，两条叠加会更热。
改法：草稿也走 300 ms debounce（`draftTimerRef` 已有 800 ms 的 `.sidelight/` 分支，`App.tsx:602-608` 可合并），并让草稿与自动保存共用**一次**序列化结果。

**O2 两段保存落点处理几乎逐行重复**
`App.tsx:1593-1612`（`performCommit`）与 `App.tsx:1641-1659`（`performSaveAs`）是同一段四分支逻辑，只有两处句子不同（`请用「另存为」选择位置` / `请换一个支持选择保存位置的浏览器`）。三处重复序列化是 STATE.md 已知项，这一处是新的一处。
改法：抽一个 `commitViaPicker(normalized, withEol, { unsupportedHint })`，两处调用。

**O3 两份菜单键盘逻辑重复，「最近打开」要加的左右键会变第三份**
`FileMenu.tsx:84-106`（文件菜单）与 `App.tsx:2511-2531`（导出菜单）各自实现一套 ↑↓ / Home / End / Tab / Esc。U4 若改成 flyout 还要再加 →←。
改法：抽 `useMenuKeyboard(menuRef, { onClose, orientation })`，两处共用。若 U4 采用内联方案，这一条可以并入下一轮，不阻塞。
