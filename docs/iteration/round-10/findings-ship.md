## 2. roundtrip 口径：三栏表与替换表

### 2.1 为什么现在的「3 / 7」不能继续用

现在是 3 / 7 完全保真（03、05、07）。但「保真」在不同路径下含义不同，混成一个数会失真：

- 02 的差距是**表格区块**（分隔行 + 列宽 + 表格前后 2 个空行），富文本路径可以修到零差异；源码路径本来就零差异。
- 04 的差距是**定义块**：富文本路径必然删定义；源码路径写回原文，零差异。
- 01、06 只差空行，**保存门根本不拦**（`blank-lines` 是 `blocking: false`）。现在报告没说这一点，读者会以为它们被拦住了。

实测（`node --experimental-strip-types .tmp/ship-risk-kinds.mjs`，用 `src/lib/risk.ts` 的 `classify` / `baselineLosses` 跑当前保存流程）：

```text
01-obsidian-note.md  identical=false  losses=blank-lines                 blocking=-                 baseline=0
02-table.md          identical=false  losses=table-separator,blank-lines  blocking=table-separator   baseline=1
03-footnotes.md      identical=true   losses=-                          blocking=-                 baseline=0
04-reference-links.md identical=false losses=reference-links×2,blank-lines blocking=reference-links baseline=2
05-html-block.md     identical=true   losses=-                          blocking=-                 baseline=0
06-task-list.md      identical=false  losses=blank-lines                 blocking=-                 baseline=0
07-math.md           identical=true   losses=-                          blocking=-                 baseline=0
```

即：**富文本 3 / 7（测出）；源码路径 7 / 7（按定义等值，条件见 2.2）；富文本首次保存拦截 2 / 7（测出：02、04）**。三个数都真实，只是不能相加。源码路径那一栏目前不是独立测出来的能力，报告里必须带条件，否则等于用「定义等值」冒充「实测保真」。

## S1（发布·体积）余量够：40,458 B 能装约 140–190 KB 新 JS，本轮只用得到 3–8 KB

**证据。**

- 当前产物体积（`dist/`，18 个文件 1,404,769 B）：JS `index-CrNEvjJ4.js` **1,133,427 B**（gzip 348,254 B，0.307）、CSS 56,183 B、KaTeX 字体 213,664 B / 15 个 woff2。
- 安装包 809,542 B，硬线 850,000 B（`packaging/installer.ps1:93-105` 超线 exit 1）→ 余量 **40,458 B**。
- NSIS 压缩：`SetCompressor /SOLID lzma` + 字典 32 MB（`packaging/installer.nsi:29-30`），载荷 = `host/bin` 五件 1,020,452 B + `dist` 1,404,769 B + 图标/README/LICENSE。
- 用 Python `lzma`（XZ preset 9）逐件实测（`.tmp/size-probe.py`）：

```text
dist js                     raw=1,133,427  lzma=293,212  ratio=0.259
dist css                    raw=   56,183  lzma= 12,348  ratio=0.220
KaTeX woff2 ×15             raw=  213,664  lzma=214,564  ratio≈1.00（已压缩，几乎不缩）
host Core.dll               raw=  703,328  lzma=101,916  ratio=0.145
host WebView2Loader.dll     raw=  194,912  lzma= 81,560  ratio=0.418
host Sidelight.exe          raw=   82,944  lzma= 30,588  ratio=0.369
合计                        raw=2,423,726  lzma=752,280  ratio=0.310（实际安装包 809,542，归档开销 7.6%）
```

- 新增代码的**边际**压缩率（`.tmp/size-probe2.py`，把真实 bundle 尾段当样本）：尾部 5,668 B → 1,188 B（0.210）；34,003 B → 7,524 B（0.221）；113,343 B → 31,032 B（0.274）；新写 6,000 B 代码样文本 → 安装包 +约 1,153 B。

**影响。** 余量够，且不是勉强够：按 0.21–0.28 的边际率加 7.6% 归档开销，40,458 B 可容纳 **约 140–190 KB** 新 minified JS；保守按 0.35 也有 115 KB。本轮预计新增：

| 改动 | 预计 minified JS | 安装包增量 |
| :--- | ---: | ---: |
| 表格整块复用（签名 + 原文块记录 + 替换） | +2.5–5 KB | +0.7–1.5 KB |
| frontmatter 后空行 | +0.3–0.8 KB | +0.1–0.3 KB |
| 列表间空行（若做） | +0.5–1.5 KB | +0.2–0.5 KB |
| 源码默认打开 + 横幅文案 | +0.5–1.5 KB | +0.2–0.5 KB |
| 合计 | **+3–8 KB** | **+1–3 KB** |

**建议预算（写进计划门禁）：**

- 软线：本版 JS ≤ 1,153,000 B（+20 KB），安装包 ≤ 820,000 B；超软线先查是不是把测试/文档打进 bundle。
- 硬线：安装包 < 850,000 B 不变（`installer.ps1` 已守）。
- 另记两条守恒量：KaTeX 字体已压缩，**加字体 1 B 就是安装包 1 B**；`dist` 里 15 个 woff2 是包体第二大头。
- 不要用「体积还早」当理由在本轮塞 KaTeX 惰性化或换解析器：那是 100 KB 级改动，得单独一轮 + ADR。

**难度：** S（只需在计划里写死两条线，验收时称重）。

## S3（风险）表格保真只对「未改表格」生效；改过之后会静默重排，保存门不会拦

**证据。**

- 表格损失的 key 只有表头单元格：`src/lib/risk.ts:90-125`，`key: table:${splitCells(header).join('|')}`；值变、增删行、删表都不算损失（`src/lib/diff.test.ts:106-117` 就是这个断言）。
- 保存门只拦「基线里已有、且当前仍命中同一 key」的损失：`src/lib/risk.ts:294-309`（`baselineLosses` 只留 `blocking`；`activeLosses` 取交集，基线为空永远返回空）。
- 基线在**载入时**用「原文 vs 编辑器序列化」算：`src/App.tsx:800-804`（宿主）与 `1499-1506`（浏览器/文件夹）。序列化走 `serializeBody`（`App.tsx:148-150`）。
- 因此：表格复用一旦落进 `serializeBody`（或载入时的同一序列化路径），02 的基线里就不再有 `table-separator`。用户此后给表格加一列，序列化会重排分隔行，但 `activeLosses` 的基线集合里没有它 → **不弹**。今天 `02` 的基线是 `1`（实测 `.tmp/ship-risk-kinds.mjs`），落地后变 `0`。
- 反过来，如果只把复用放在「保存时的 `currentMarkdown`」而基线仍用纯序列化，则 02 的基线保留 `table-separator`，用户改表格仍会弹——行为和“修好了”不一致。**落点决定行为，计划必须指定落点。**

**影响。**

- 对外：如果 README/CHANGELOG 写「表格保真」，用户会以为「我改表格也不怕」，实际改完一次就回退到重排。必须写边界句（见 S2）。
- 对内：保存门少了一类保护，属于可接受的功能取舍，但要在 ADR-0010 里写明，避免下一轮有人把它当回归修。

**建议。**

1. 计划里明确：复用同时用于「载入基线序列化」与「保存序列化」，否则 02 不可能到保真。
2. 若想保留提示，加一个**保存时计算**的非阻塞类别（例如 `table-reformatted`，`blocking:false`），在状态栏或保存成功提示里说「表格已重新排版」。不要设 `blocking:true`：那会退回第 7 轮被否掉的「每次保存都弹」。
3. README/CHANGELOG 用这句：「没动过的表格原样写回；改过单元格、增删行列或改对齐的表格会按编辑器规范重新排版，这条不弹确认。」
4. 验收加两条反例：未改表格保存字节不变；改一格后再保存，分隔行**变了**且**没有**确认框（预期行为，记录在案）。

**难度：** S（文档与验收）；M（若要非阻塞提示）。

## S4（风险）源码默认打开的边界：必须「载入即源码」；横幅「在源码模式打开原文」在已编辑时会丢改动

**证据（实测，`.tmp/ship-evidence.json` + `shots/round-10/ship-0*.png`）。**

- 干净载入 demo 文档「参考与出处.md」→ 横幅出现；点「在源码模式打开原文」→ 源码框内容含定义块：

```text
sourceHasRefDefinitions=true  sourceHasRefSyntax=true
sourceHead="# 参考与出处\n\n…官方文档在 [Tiptap][tiptap]，内核是 [ProseMirror][pm]。\n\n[tiptap]: https://tiptap.dev\n[pm]: https://prosemirror.net"
```

- 先在富文本里敲两个字，再点「源码」→ 源码显示的是**整理结果**，定义块已消失，多出的字还在：

```text
afterEditSourceHasDefs=false  afterEditSourceHasTypedText=true
afterEditSourceHead="…官方文档在 [Tiptap](https://tiptap.dev)，内核是 [ProseMirror](https://prosemirror.net)。追加"
```

- 在同一个「已编辑」状态点横幅的「在源码模式打开原文」→ 源码变回原文，**刚敲的字不见了**：

```text
reopenOriginalHasTypedText=false  reopenOriginalHasDefs=true
```

- 代码对应：源码视图保存直接返回 `sourceText`（`App.tsx:1780-1785`）；进源码时只有在「未脏或草稿恢复」才取 `rawTextRef`（`App.tsx:2705-2714`）；横幅按钮无条件取 `rawTextRef`（`App.tsx:2730-2738`）。源码内容写回正文时按保存基线重算 dirty（`App.tsx:2694`）。
- 由此推断（代码路径，未在宿主实测）：已编辑 → 点横幅按钮 → 源码恢复原文 → `Ctrl+S` 时 `prepareSave` 的 `normalized` 等于 `originalText`，`activeLosses` 返回空（`App.tsx:1884-1889`）→ **不弹确认，直接写回原文，富文本里的改动被静默丢掉**。

**影响。** 如果本轮按简报做「含定义块默认源码模式（或强提示）」，最安全的实现是**载入时**直接进源码；不要靠「让用户点横幅按钮」来救，因为该按钮在已编辑时会制造丢改动路径。这条也解释了为什么「源码路径保真」必须带「进源码前未编辑」的条件。

**建议。**

1. 默认源码只在载入路径做：判定条件用载入基线里是否有 `reference-links` 的 `blocking` 损失（现成的 `baselineLossesRef`，`App.tsx:800-804/1499-1506`），不要新写正则。
2. 草稿恢复、新建、示例文档不自动进源码；进入时显示一次性提示（横幅已有 `role="status"`）。
3. 横幅按钮在 `dirty` 时加确认：「显示原文会丢弃你刚才的编辑」，或改文案为「丢弃编辑并查看原文」。最低限度：按钮 disabled + title 说明。
4. 源码保存前若 `sourceText === rawTextRef` 且当前 dirty，提示「源码是原文件内容，保存会丢弃编辑」——这是与 S4 同源的一条守卫，可并入本轮或记下一轮。
5. 验收加一例：编辑后点横幅按钮 → 出现确认框；取消不改源码。

**难度：** S（默认源码 + 文案）；M（按钮确认守卫）。

## S5（口径可靠性）02 到「保真」需要三件事；报告脚本是手写复刻，必须与产品同步

**证据。**

- 02 的实际差异不是只有分隔行。同一份源码走当前 app 流程（`.tmp/ship-diff-detail.mjs`）：

```text
02-table.md  src=8 lines  app=10 lines
SRC: ["# 三个月的账","","| 项目 | 一月 | 二月 |","|:-----|-----:|:----:|","| 房租 | 3200 | 3200 |","| 书   | 180  | 240  |","","表格后面的一段话。"]
APP: ["# 三个月的账","","","| 项目  | 一月   | 二月   |","| :--- | ----: | :----: |","| 房租  | 3200 | 3200 |","| 书   | 180  | 240  |","","","表格后面的一段话。"]
```

  三处差异：① 分隔行被重写；② 单元格内空格（列宽）被重排；③ 表格前后各多 1 个空行。只复用分隔行，02 仍是「有变化」（只剩 ②③），报告不能写「保真」。
- 01 只差 frontmatter 结束后的 1 个空行；06 只差任务列表与普通列表之间的 1 个空行：

```text
01  src=15 → app=14（丢 "---" 后空行）
06  src=12 → app=13（多 1 空行，位于 "- [x] 已完成" 与 "- 普通条目" 之间）
```

- 报告脚本不调产品代码，是复刻：`scripts/roundtrip.mjs:28-34`（`throughApp`）自己拼 frontmatter/脚注/HTML/公式；`src/App.tsx:1780-1785`、`148-150` 是产品侧同类逻辑。两处一旦不同步，报告数字与用户看到的行为分叉。
- 现有 CHANGELOG/README 已经出现过同类漂移：`docs/CHANGELOG.md:49,61` 的「体积与校验和见 0.21.0」而 0.21.0 条目（`docs/CHANGELOG.md:24`）又写「见 0.22.0」（链式引用，读者要跳三次）；`README.md:116` 的 ADR 区间过期。

**影响。** 本轮发布承诺的核心是「02 从被拦截变保真」。若只做分隔行复用，roundtrip 会诚实显示「有变化」，但计划/CHANGELOG 可能提前写「保真」——这是发布侧最该防的虚报。若脚本忘了同步（例如复用写在 App 里而没写进 `throughApp`），则报告显示「有变化」而产品已保真，属漏报，同样要修。

**建议。**

1. 计划把 02 拆成三个验收点：分隔行复用、单元格空格复用（两者可合成「整块复用」）、表格前后空行与原文一致。缺一条就写「02 未保真」。
2. 把保存流程抽成 `src/lib/save.ts`（纯函数：原文 + 序列化结果 → 最终文本），`App.tsx` 与 `scripts/roundtrip.mjs` 都调它。这样报告测的就是产品同一段代码；不增加包体（代码搬家），还顺带减少 `App.tsx` 的重复序列化（见优化 1）。
3. `scripts/roundtrip.mjs` 加断言：`throughApp` 必须 import 自 `src/lib/save.ts`（或对同一输入断言两条路径等值）。CI 可跑 `npm run roundtrip` 并 `git diff --exit-code docs/roundtrip-report.md`，防止报告与主干脱节。
4. CHANGELOG 草稿里的 `[实测]` 不得由实施者手填猜测值；必须来自 `npm run roundtrip` 输出。

**难度：** M（抽函数 + 脚本改造，约 100 行搬家，不新增依赖）。
